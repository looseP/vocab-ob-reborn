# ADR-0025: 可携带导出契约（版本化 schema + 单一代码路径 + manifest 留痕）

- **Status**: Accepted
- **Date**: 2026-09-12
- **References**: ADR-0022（单 owner 自托管）、CONTEXT.md（Portable export）、`scripts/postgres-backup.ts`（原子写 + manifest 先例）
- **上游**: 2026-09-12 后端完备性拷问会话（第一轮 Q5=C / 第二轮裁决）

## Context

用户数据的长期价值主张是"素材即资源、空间即语义环境"，而 agent 消费导出物是明确场景。现状**只有整库 `pg_dump`**：没有任何导出端点（`src/http/routes/*` 无 `Content-Disposition`/attachment/导出服务），数据想带走只能整库搬。

导出同时也是**数据出域通道**：它把 owner 的素材、进度、笔记搬出数据库边界，因此不能只当"一个下载接口"来设计。

## Decision

1. **导出是版本化契约**：产物携带 `exportSchemaVersion`，schema 一旦发布只做加法或升版本；消费方（含 agent）**先校验版本与 sha256 再消费**。
2. **全量与分包共用同一条代码路径**：分包只是过滤参数（按词书 / 按子空间），不是第二套实现——两套实现必然腐化。
3. **复用备份的原子写 + manifest + sha256 模式**（先例 `scripts/postgres-backup.ts:295-307`）：临时文件 → 校验 → 原子 rename；manifest 记录范围、时间、条目数、sha256。
4. **通道为 owner-only，且留痕不靠新表**：导出写结构化日志，并把 **manifest 自身作为记录**（范围 + 时间 + sha256 = "导出了什么"）。**本期不建审计表**——单 owner 下"谁导出"没有信息量；将来出现多用户或第三方消费再立表（届时按 user 过滤是硬要求）。
5. **导入语义押后**：合并 / 覆盖 / 新库三种语义未决；manifest 中的实体 id 清单为将来合并留钩子。

## Tradeoffs

- **版本化契约 vs 一次性格式**：版本化要求长期维护纪律；代价换来"agent 每次都能直接消费、不用重复解释格式"。
- **单一代码路径 vs 双实现**：单一实现让"分包导出漏字段"这类漂移不可能发生；代价是全量导出必须容忍过滤参数为空。
- **manifest 留痕 vs 独立审计表**：manifest 零新表、天然与产物同寿命；代价是无法回答"上个月谁导过"这类跨产物查询（当前无此需求）。

## Consequences

- ✅ 数据可携带：换机、审查、交给 agent 三件事一次解决。
- ✅ 导出物自带校验信息，消费方能在坏文件上早失败。
- ⚠️ 导出 schema 从此有版本演进纪律；建议把"导出契约检查"并入 `api:governance` 那条链（与 `docs/api/openapi.json` 同级的快照检查）。
- ⚠️ 数据出域通道的权限面必须在实现时钉死 owner-only；将来多用户化时，按 user 过滤是**红线级**要求。
- ⚠️ 导出可能很大（L3 素材 + 全量笔记）：需要体量预算与流式写入，不能一次性拼进内存。
