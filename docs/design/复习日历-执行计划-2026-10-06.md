## 一、M1 · 真 forecast（修掉 V10 类假指标）

1. **仓库**（`src/repositories/stats.repository.ts`，照 `getDashboardSummary` 的形制）新增：
   `getDueForecast(userId, wordbookId, horizons: number[]): Promise<Array<{ horizonDays: number; count: number }>>`
   - 口径：`state <> 'suspended' AND due_at > <今天00:00 显示时区> AND due_at <= <今天00:00 + horizonDays 天>`（**日历日口径**，与 `dueToday` 一致；不是从 now 起滚动的 168 小时）。
   - 判据（写进测试）：每个数字 == 一条 SQL 直查。
2. **服务**（`stats.service.ts`）：`computeForecast` 保留为纯函数但改吃真实入参（`dueNow` 沿用 summary.dueToday；`due7d/due14d` 来自 `getDueForecast([7,14])`）；依赖注入照 `withActorStats` 既有模式。
3. **契约**：dashboard 响应结构**不变**（`dueNow/due7d/due14d` 三字段），只换数值来源 → 零 openapi 变化（不触 breaking 门禁）。
4. **测试**：repo 集成（真库桶计数 + 挂起词不计入）、service 单测（注入假桶）、**对账断言**（`due7d` == SQL 直查）。

## 二、M2 · 日历视图（过去 + 未来 + 今天）

1. **新薄路由** `src/http/routes/review-calendar.ts`（**新文件** + `ROUTE_COMPLEXITY_BOOTSTRAP_LIMITS` 登记，上限=实测行数）：
   - `GET /api/review/stats/calendar?days=30`（读 `owner/agent/none`）→
     `{ past: [{date, reviewed}], today: {dueNow, reviewedToday}, future: [{date, due}] }`
     - `past`：`review_logs.reviewed_at` 按显示时区日历日分桶（复用 heatmap 的查询基因）；
     - `future`：`due_at` 按日历日分桶（`state <> 'suspended'`）；
     - `today`：两值都给（已复习 x / 待做 y）。
   - `GET /api/review/day?date=YYYY-MM-DD&scope=due|reviewed&limit=50`（读）→
     `{ date, scope, total, items: [{ id, slug, title, lemma, short_definition }] }`
     - `scope=due`：该日历日到期的词（前 N + total）；
     - `scope=reviewed`：该日复习过的词（来自 `review_logs`，去重按词）。
2. **登记**：operations.ts 两条（读面）、响应契约 `review-calendar-response-contract.ts`（`.strict()`）、server.ts 挂载、openapi + 前端客户端再生。
3. **前端**（`DashboardPage.tsx`）：日历区（月视图或 30 天条带，风格延续 `MasteryHeatmap`：过去=已复习量、未来=到期量、今天=双值徽标）；点某天 → `GET /review/day` 弹层列词（**只读列表，不进复习流**）。

## 三、红线

- **只读**：两处端点零写入；不改调度、不写 FSRS、不动 `review_logs`/`user_word_progress`。
- **不发明指标**：每个展示数字可回溯到一条 SQL（对账断言进测试）。
- **不掺和 hulu**：计划进度/剩余轮数只在计划页，日历不做第二个"计划视图"。
- **日历日口径**：Asia/Shanghai（沿用 `db/timezone` 既有工具），不用 UTC 日界。
- 新端点新文件（路由棘轮）；不动受冻结的 `review.ts`。

## 五、明确不做

- 不改 `MasteryHeatmap` 既有行为（日历区是并列新增）。
