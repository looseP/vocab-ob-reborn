## F-1 `payload.bodyMd` 命名易误读

- **事实**：导出 JSON 块的 `bodyMd` 存的是**渲染后正文**——marker 已被替换为引用块
  （`src/services/l3-study-note-export.service.ts`：renderBody 产出即 payload 的 bodyMd），
  不是用户输入的原始 markdown。
- **风险**：字段名读作「原始正文」，导入/回写方会误以为可原样还原 marker，实际 marker 已丢失。
- **归属**：Task 10 遗留命名，Task 11 未引入也未改。
- **处置建议**：在类型注释标明「渲染后」，或在 N2 引入新引用型（必然改动 payload 形状）时一并改名
  为 `renderedBodyMd` 并升 `exportSchemaVersion`。**单独改名会破坏 v1 导出兼容，不做。**

## F-2 快照缺失时来源清单不列该引用

- **事实**：marker 对应的引用行在 repository 中不存在时，正文保留占位块
  （`> **引用 · 未找到快照**`），但**来源清单不列该条**、也不凭 repository 其它引用行回填。
- **风险**：行为本身合理（无快照可列），但任务书与 ADR 未述及，后来者可能误判为缺陷并「修复」成回填。
- **归属**：N1 既有行为，Task 11 新增测试固化（`tests/services/l3-study-note-export.test.ts`
  「缺失引用快照」）。
- **处置建议**：在下一次触碰导出文档时补一行说明；N2 新增引用型时沿用同一规则
  （清单只列正文实际渲染成功的引用）。

## F-3 范围变更应在实现期同步登记

- **事实**：Task 10 的侧栏导出出口属超范围实现，实现期未登记，直到正式审查才发现（P2-1），
  本次以「合并后补登记」（任务书 §7 / 台账 §8）收口。
- **风险**：事后追认会留下「实现与决策不同步」的窗口——审查是最后一道发现关口，不该承担登记职责。
- **处置建议**：后续每批任务书的开工清单加入一条——**任何偏离任务书 §1 决策表的实现，必须先登记再提交**。
